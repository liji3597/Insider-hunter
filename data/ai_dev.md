# AI 协作开发流程

> 本文档定义了 AI 与用户协作开发的完整流程，包括各阶段的职责、输出物和控制点。

---

## 一、启动方式
回答语言：强制必须用中文回答用户的问题或与用户沟通

用户输入：
```
请按照 /ai_dev 流程，帮我开发一个 [功能/模块名称]
```

或：
```
请先阅读以下文档了解项目：
- docs/00_架构设计/项目概览.md
- docs/04_模块规格/相关模块.md

然后按 /ai_dev 流程开发：[功能描述]
```

---

## 二、完整工作流程

### 阶段 0: 上下文准备

**AI 动作**：
- 阅读项目概览、相关模块规格
- 阅读 `docs/05_经验沉淀/常见问题.md`（如存在）
- 了解现有设计风格和约定

**输出**：理解确认 + 澄清问题

**👤 用户检查点**：回答问题，确认理解正确

---

### 阶段 1: 需求分析与设计

**AI 动作**：

1. **多角色深度讨论**：

   | 角色 | 关注点 |
   |------|--------|
   | 产品经理 | 用户价值、业务目标 |
   | 架构师 | 系统兼容、技术可行 |
   | 测试工程师 | 边界条件、异常场景 |
   | 用户代言人 | 使用体验、操作便捷 |

2. 输出讨论记录和最终决策

3. 创建 `docs/01_需求设计/[模块]需求设计.md`

**输出**：需求设计文档 + 假设清单 + 讨论记录

**👤 用户检查点**：审批需求设计，确认假设

---

### 阶段 2: 可行性评估

**AI 动作**：
- 技术可行性分析
- 工作量预估
- 风险识别
- 与现有模块的依赖分析

**输出**：可行性评估（简报形式，不需要单独文档）

**👤 用户检查点**：确认继续 / 要求调整

---

### 阶段 3: 技术设计

**AI 动作**：

1. **多角色深度讨论**：

   | 角色 | 关注点 |
   |------|--------|
   | 架构师 | 整体架构、模块边界 |
   | DBA | 数据库设计、索引、性能 |
   | 后端开发 | 接口设计、核心逻辑 |
   | 安全工程师 | 权限、数据安全 |

2. 创建 `docs/02_开发计划/[模块]技术设计.md`

**输出**：技术设计文档

**👤 用户检查点**：审批技术方案

---

### 阶段 4: 开发任务规划

**AI 动作**：
- 任务细粒度拆解
- 依赖关系分析
- 优先级排序
- 创建 `docs/02_开发计划/[模块]开发任务.md`

**输出**：开发任务文档

**👤 用户检查点**：确认任务划分

---

### 阶段 5: 开发实现

**AI 动作**：
- 按任务逐步开发
- 遇到问题即时沟通
- 记录变更
- 每完成一批任务报告进度

**变更处理**：
- 小变更：直接修改 + 记录
- 中变更：暂停，向用户确认
- 大变更：回退到设计阶段

**👤 用户检查点**：代码审查，确认继续

---

### 阶段 5.5: 二次校验

> 开发完成后，对照设计文档逐项校验实施内容

**AI 动作**：

1. **文件清单校验**：
   - 对照技术设计文档“代码变更清单”
   - 检查新增文件是否全部创建
   - 检查修改文件是否全部完成

2. **接口校验**：
   - 对照技术设计文档“接口设计”
   - 检查所有接口是否已实现
   - 检查接口路径/参数是否一致

3. **业务逻辑校验**：
   - 对照技术设计文档“业务流程图”
   - 检查每个流程节点是否有对应代码
   - 检查异步处理、热度规则等细节

4. **编译验证**：
   - 执行 `mvn compile -DskipTests`
   - 确认无编译错误

5. **输出校验报告**：
   - 记录检查结果（通过/缺失/偏离）
   - 缺失项立即补充实现
   - 偏离项向用户确认是否调整

**校验报告格式**：

```markdown
## 二次校验报告

| 类别 | 状态 | 备注 |
|------|------|------|
| DDL 脚本 | ✅/❌ | |
| 新增文件 (x项) | ✅/❌ | |
| 修改文件 (x项) | ✅/❌ | |
| 接口实现 (x项) | ✅/❌ | 缺失: xxx |
| 业务逻辑 (x项) | ✅/❌ | |
| 编译验证 | ✅/❌ | |

### 发现的问题
- 问题 1: xxx
- 问题 2: xxx

### 处理结果
- 问题 1: 已补充实现
- 问题 2: 待用户确认
```

**👤 用户检查点**：确认校验结果，处理缺失/偏离项

---

### 阶段 6: 验证测试

**AI 动作**：
- 执行 DDL 脚本（或提示用户执行）
- 编写并执行 Python 测试脚本
- 边界条件验证

**输出**：测试报告

**👤 用户检查点**：确认测试通过

---

### 阶段 7: 文档交付

**AI 动作**：
- 创建/更新 `docs/03_接口文档/[模块]接口文档.md`
- 创建/更新 `docs/04_模块规格/[模块]规格.md`
- 更新 `docs/05_经验沉淀/常见问题.md`（如有新坑）
- 输出 walkthrough 总结

**👤 用户检查点**：最终验收

## 四、变更处理流程

```
发现问题/收到变更请求
         │
         ▼
┌─────────────────────┐
│ 评估影响            │
│ ─────────           │
│ 小：直接修改        │
│ 中：向用户确认      │
│ 大：回退设计阶段    │
└─────────────────────┘
         │
         ▼
更新变更记录章节
```

## 五、协作原则

1. **主动沟通**：遇到不确定的问题主动询问，不自行假设
2. **最小可行**：优先实现 MVP，扩展功能标记为"待开发"
3. **假设透明**：所有假设必须记录并请用户确认
4. **阶段门禁**：每个阶段必须经用户审批才能进入下一阶段
5. **持续记录**：变更、问题、经验都需记录

## 六、产物规范

### 6.1 SQL 脚本规范

**存放位置**：`ruoyi-vue-pro/sql/mysql/`

**命名格式**：`V{版本号}__{描述}.sql`

| 格式说明 | 示例 |
|----------|------|
| V001__初始化.sql | 最初的表结构 |
| V002__social_extension.sql | 社交扩展功能 |
| V003__point_bonus.sql | 积分奖励功能 |

**版本号规则**：
- 使用三位数字，从 001 开始递增
- 双下划线 `__` 分隔版本号和描述
- 描述使用小写字母和下划线

**脚本头部模板**：
```sql
-- =============================================
-- 功能: [功能名称]
-- 版本: V{版本号}
-- 日期: YYYY-MM-DD
-- 依赖: V{前置版本号} (如有)
-- =============================================
```

**导入顺序**：按版本号从小到大依次执行

## 七、知识传承

> 每次开发完成后，必须进行经验沉淀，确保踩过的坑不再重复

### 7.1 触发时机

在以下情况下执行经验沉淀：
- 阶段 7 文档交付时
- 遇到并解决了非预期的问题时
- 用户明确要求总结经验时

### 7.2 操作流程

**步骤 1: 识别可沉淀的经验**

回顾开发过程，识别以下类型的经验：
- 踩过的坑和解决方案
- 框架规范和约定
- 代码模式和最佳实践

**步骤 2: 确定沉淀目标文件**

| 经验类型 | 目标文件 | 格式要求 |
|----------|----------|----------|
| 问题与解决方案 | `docs/05_经验沉淀/常见问题.md` | 追加到对应分类章节 |
| 设计模式/架构模式 | `docs/05_经验沉淀/设计模式.md` | 追加到对应章节 |
| 模块规范 | `docs/04_模块规格/` | 更新规格文档 |

**步骤 3: 追加而非新建**

```markdown
# ❌ 错误做法
创建新文件 task_module_experience.md

# ✅ 正确做法
追加到已有的 常见问题.md 对应章节
```

**步骤 4: 更新变更记录**

在 `常见问题.md` 的变更记录表格追加一行：
```markdown
| 2025-12-24 | Controller 路径规范、多租户过滤、JDK 8 兼容性 |
```

### 7.3 常见问题格式规范

```markdown

**问题**：[现象描述]

**原因**：[根因分析]

**解决方案**：
```代码或配置示例```

---
```
